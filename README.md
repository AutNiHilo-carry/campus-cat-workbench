# 大学猫协一站通 · Campus Cat Workbench

面向高校猫咪保护协会的协作工作台。将猫咪档案、救助、寄养、绝育、领养回访，以及物资清点、财务和工作总结汇总在一起，方便记录和统计零散的工作。

由 **复旦大学爱和猫协** 发起并维护。**首次使用前请联系微信 `HaruAurora_Carry`，说明使用主体与用途；发送联系信息后即可使用，无需等待回复或书面批准。** 具体条款见 [使用前联系许可](LICENSE)。欢迎各位同仁提供宝贵意见。

> **项目状态：轻量级测试 Demo，仍在开发和完善中。** 当前主要用于功能展示、流程讨论、学习交流和小规模测试；可能存在未发现的缺陷、边界情况和兼容性问题。已有测试不等于完成全面安全审计、公网渗透测试、容量压测或真实生产验证。感兴趣的相关组织欢迎参与测试并提供意见。
>
> **当前不推荐部署上线，也不推荐引入真实业务数据。请仅使用虚构或充分脱敏的资料进行本地体验和隔离测试，不要录入真实领养人信息、协议、财务账目或账号凭据。** 本项目不提供生产可用性、数据零丢失、持续维护或响应时效承诺；未来接口、数据结构和界面仍可能调整，更新前应备份并验证迁移。

## 试用与账号

**本仓库提供代码，不是已开通账号的在线服务。** 使用协作版需要先启动本地服务或由维护者部署；静态演示版的数据仅保存在当前浏览器，不提供多人账号协作。

- **首次进入协作版**：创建自己的管理员账号，项目没有默认账号或默认密码。生产部署还需由维护者提供初始化口令。
- **邀请成员**：管理员通过“管理 → 账号与权限”创建独立账号，并分配管理员、财务、领养负责人、成员或只读角色。
- **查看范围**：财务明细按角色及本人报销归属限制；领养协议仅管理员和领养负责人可访问。其他业务资料在协会内共享，使用真实信息前请确认成员范围。
- **修改或忘记密码**：已登录用户可修改本人密码；忘记密码请联系本系统管理员重置。修改或重置后，该账号全部旧会话失效，需要重新登录。

所有管理员都无法登录时，服务器维护者可停服后执行本机恢复。具体步骤与完整角色规则见 [账号恢复与权限矩阵](ACCOUNT-RECOVERY.md)。

## 适合谁使用

- **猫协负责人**：集中掌握各项事务，保留业务经历、操作记录与交接资料。
- **救助、寄养及领养成员**：围绕同一只猫持续跟进，记录不同阶段的情况、照片与回访。
- **物资与财务负责人**：管理不同地点库存、器材借还、文创销售、垫付审核和收付款登记。
- **高校开发者和公益技术团队**：复用已有界面与业务流程，适配本校的组织分工和管理习惯。

## 核心功能

| 模块 | 主要能力 |
| --- | --- |
| 猫咪档案 | 维护基本情况、性格描述、病史与绝育情况；保存头像、照片备注、历史经历和猫咪轶事；关联曾用名及业务记录。 |
| 救助与寄养 | 跟进待救助、就医及结束去向；允许先记录匿名求助，再补档案；保存多段寄养地点、照护人和交接经历。 |
| 绝育管理 | 按待绝育、住院中、已放归查看；登记医院、手术日期、费用与放归信息；住院时校验必填信息。 |
| 领养与回访 | 区分有无意向领养人、已领养及历史经历；维护领养文案、发帖日期与协议；每次回访独立保存文字和照片，并归档回访相册。 |
| 物资与文创 | 分开管理日常与文创物资，支持多个存放地点、可选照片、领用和盘点；器材借出归还保留流水；线上订单与线下活动分开登记。 |
| 财务管理 | 记录收入、协会支出、个人垫付与协会欠款；审核后再登记报销或结清；文创订单关联收入，防止重复确认。 |
| 工作总结 | 按实际业务日期自动汇总救助就医、绝育、领养等工作；查看来源记录，补充说明，并导出交接资料。 |
| 协作与追溯 | 独立账号和角色权限、冲突提示、操作审计、回收站、附件访问控制，以及业务备份和系统备份。 |

电脑端提供表格与详情视图，手机端使用适应窄屏的卡片、导航和可滚动弹窗。列表支持分页、搜索和业务状态筛选。

## 使用场景示例

### 场景一：跟进一只受伤猫咪，直到找到领养人

成员发现一只受伤的猫，先登记发现地点和受伤情况。治疗结束后如果需要寄养，视情况补充猫咪档案。选择“转寄养”，系统会建立待安置记录。找到领养人后，可继续记录领养日期、协议和后续回访；每次回访的文字与照片都会保留下来，方便下一位成员接手。

### 场景二：卖出一份猫协文创，核对库存和收入

有人在线预订一份文创，成员登记订单后，系统会预留对应数量，避免重复卖出。实际发货或自提交付时，再扣减库存并记录出库流水。订单同时关联一笔待确认收入，由财务核实收款后确认入账。

**后续计划**：接入微店 API，让店铺订单自动同步到工作台，减少逐笔录入；订单状态、商品和库存的对应关系将按平台实际开放能力逐步接入。目前仍需手动登记。

### 场景三：成员垫付猫粮费用，交给财务审核报销

成员先自行付款购买猫粮，再提交个人垫付记录，填写用途与金额。财务核对后审核，通过后进入待报销流程；实际完成报销时，再登记付款日期和已报销状态，便于区分“已经审核”和“已经付款”。

**后续计划**：如果协会已在其他表格或应用中维护报销表，可接入对应应用的 API，将报销记录同步到工作台，减少重复填写。审批和付款状态的同步需核对原应用字段与权限，目前尚未接入。

上述流程用于记录和核对，**系统不执行支付或转账**。

## 数据保存与备份

业务记录与照片需要一起备份。界面导出的业务备份包含业务记录和附件，恢复时保留目标站点账号；系统备份还包含账号与权限，恢复后需要重新登录。

管理员可在管理菜单查看服务器备份状态或手动创建备份。**同一服务器上的备份还需要另存异地副本**，不能将其视为完整容灾保障。

我们提供了使用虚构数据的隔离恢复演练，验证账号、业务记录、照片、协议和权限能否一起恢复。步骤及限制见 [备份恢复演练](RECOVERY-DRILL.md)，真实环境仍需单独验证。

## 技术与实现（开发者阅读）

### 本地运行

推荐使用 **Node.js 24 LTS**，当前运行服务无需安装 npm 依赖。

```sh
git clone https://github.com/AutNiHilo-carry/campus-cat-workbench.git
cd campus-cat-workbench
npm test
npm start
```

启动后访问 `http://127.0.0.1:8787/`。Windows 也可运行 `start-local.cmd`。

本地模式默认加载示例数据。如需从空数据库开始，在首次启动前设置 `DANMIAO_SEED=empty`。改变此配置不会清空已经存在的数据库。

完整使用说明见 [本地协作说明](LOCAL-BACKEND.md)，服务器配置、HTTPS 与回滚步骤见 [部署指南](DEPLOYMENT.md)。GitHub Pages 仅适用于静态演示版。

### 技术架构

| 层次 | 实现 |
| --- | --- |
| 前端 | 原生 HTML、CSS、JavaScript；响应式布局，无前端框架运行依赖。 |
| 后端 | Node.js 24 内置 HTTP 模块；JSON API、会话管理与业务校验。 |
| 共享业务规则 | `shared-domain.js` 同时供前后端使用，处理迁移、回访日期、库存预留、财务汇总与月度联动。 |
| 数据库 | Node.js 内置 SQLite；业务记录以 JSON 存储，事务写入、审计和增量同步日志集中管理。 |
| 附件 | 本地持久目录；通过需要登录且校验权限的接口读取照片和协议。 |
| 备份 | SQLite 一致快照、附件复制和 SHA-256 校验；自动备份在工作线程中执行。 |
| 验证 | Node.js 内置测试框架、业务回归脚本、GitHub Actions；另有浏览器实际操作验证。 |
| 部署 | Docker Compose + Caddy；单实例服务、持久化 volume、反向代理与 HTTPS。 |

#### 写入、查询与同步

- **按记录写入**：仅更新实际发生变化的业务记录，一个操作涉及的库存、收入及关联记录在同一事务内处理。
- **服务端分页**：数据库完成搜索、筛选和分页；同组物资的不同存放地点一起展示。
- **增量同步**：日常保存及轮询传输变更记录；版本过旧、跨日或变更过大时回退到完整快照。
- **并发保护**：修改附带旧版本，冲突时拒绝覆盖；幂等请求编号防止同一次提交重复记账。
- **共享规则**：后端直接调用纯业务模块，运行时不再加载界面脚本或模拟 DOM。

接口变更、验证范围与性能边界见 [升级说明](UPGRADE-NOTES.md)。为兼容早期配置，环境变量目前保留 `DANMIAO_` 前缀。

#### 会话与安全

密码使用 scrypt 加盐哈希；登录采用 HttpOnly、SameSite Cookie 与 CSRF 校验。生产模式要求 HTTPS 站点来源、首次管理员初始化口令和空数据初始化，并启用 Secure Cookie。权限由服务端执行，界面按钮不是权限校验的依据。

改密、管理员重置和本机恢复会撤销目标账号的全部会话，并记录不含密码的审计；登录验证完成后会再次核对账号状态，避免并发改密后使用旧验证结果创建会话。

#### 数据目录与备份配置

默认业务目录为 `data/`，可通过 `DANMIAO_DATA_DIR` 调整。实际数据库、上传附件、密钥、日志和备份均不应提交到 Git；仓库已配置相应忽略规则。

生产配置默认每24小时在独立目录创建系统备份。快照、附件校验、停服切换和回滚流程见 [部署指南](DEPLOYMENT.md)。

### 技术边界与后续方向

当前版本定位于小规模猫协内部协作的单实例底座。首次登录仍读取一次可见业务快照，跨模块写入也会检查完整业务状态；列表查询与日常同步已分页或增量化。正式使用前仍需在实际服务器验证 HTTPS、附件上传、备份恢复与负载情况。

目前不包含在线支付、邮件找回密码、自动异地备份、对象存储或多服务器高可用。后续可继续拆分首次载入与详情查询，逐步引入类型检查，并根据实际规模评估 PostgreSQL、私有对象存储和监控告警。容器构建由 GitHub Actions 校验；实际服务器的 HTTPS 和公网运行仍需部署后验证。
