# 大学猫协一站通 · Campus Cat Workbench

面向高校猫咪保护协会的协作工作台。将猫咪档案、救助、寄养、绝育、领养回访，以及物资清点、财务和工作总结汇总在一起，方便记录和统计零散的工作。

由 **复旦大学爱和猫协** 发起并维护。**首次使用前请联系微信 `HaruAurora_Carry`，说明使用主体与用途；发送联系信息后即可使用，无需等待回复或书面批准。** 具体条款见 [使用前联系许可](LICENSE)。欢迎各位同仁提供宝贵意见。

> **项目状态：轻量级测试 Demo，仍在开发和完善中。** 当前主要用于功能展示、流程讨论、学习交流和小规模测试；可能存在未发现的缺陷、边界情况和兼容性问题。已有测试不等于完成全面安全审计、公网渗透测试、容量压测或真实生产验证。感兴趣的相关组织欢迎参与测试并提供意见。
>
> **当前不推荐部署上线，也不推荐引入真实业务数据。请仅使用虚构或充分脱敏的资料进行本地体验和隔离测试，不要录入真实领养人信息、协议、财务账目或账号凭据。** 本项目不提供生产可用性、数据零丢失、持续维护或响应时效承诺；未来接口、数据结构和界面仍可能调整，更新前应备份并验证迁移。

## 适合谁使用

主要面向猫协核心成员，包括负责人及救助、领养、物资、财务等事务的实际管理者，**暂不面向普通社员**。

- **猫协负责人**：集中掌握各项事务，保留业务经历、操作记录与交接资料。
- **救助、寄养及领养成员**：围绕同一只猫持续跟进，记录不同阶段的情况、照片与回访。
- **物资与财务负责人**：管理不同地点库存、器材借还、文创销售、垫付审核和收付款登记。
- **高校开发者和公益技术团队**：复用已有界面与业务流程，适配本校的组织分工和管理习惯。

## 核心功能

下表概述项目已有模块；本地模拟版可体验业务界面与流程，真实账号权限、服务端审计及系统备份属于实验性后端能力。

| 模块 | 主要能力 |
| --- | --- |
| 猫咪档案 | 维护基本情况、性格描述、病史与绝育情况；保存头像、照片备注、历史经历和猫咪轶事；关联曾用名及业务记录；按全部、寄养中、已领养、已去喵星筛选，经历按时间排序并支持折叠。去喵星登记日期与登记时间，头像显示为黑白。 |
| 救助与寄养 | 跟进待救助、就医及结束去向；允许先记录匿名求助，再补档案；救助列表可添加和查看现场照片；保存多段寄养地点、照护人和交接经历。 |
| 绝育管理 | 按待绝育、住院中、已放归查看；现场照片辅助辨认与定位；术前住院可先填医院，实际手术日期和费用可后补；完成手术后同步档案绝育状态，按实际手术日期计入工作。 |
| 领养与回访 | 区分有无意向领养人、已领养及历史经历；维护领养文案、发帖日期与协议；每次回访独立保存文字和照片，并归档回访相册。 |
| 物资与文创 | 分开管理日常与文创物资，支持多个存放地点、可选照片、领用和盘点；器材借出归还保留流水；线上订单与线下活动分开登记。 |
| 财务管理 | 记录收入、协会支出、个人垫付与协会欠款；审核后再登记报销或结清；文创订单关联收入，防止重复确认。 |
| 工作总结 | 按实际业务日期自动汇总救助就医、绝育、领养等工作；查看来源记录，补充说明，并导出交接资料。 |
| 活动与赞助（测试） | 记录即将开展的活动、时间地点、负责人及人员分工；跟进赞助方、支持内容和落实状态，可关联活动。支持筛选、分页和回收站恢复。 |
| 首页公告 | 管理员发布公告后在首页轮播；同一浏览器首次遇到未读内容时弹出公告栏，内容更新后再次提醒；支持草稿及撤下。 |
| 协作与追溯 | 独立账号和角色权限、冲突提示、操作审计、回收站、附件访问控制，以及业务备份和系统备份。 |

电脑端提供表格与详情视图，手机端使用适应窄屏的卡片、导航和可滚动弹窗。列表支持分页、搜索和业务状态筛选。

档案可单独标记寄养或领养，并选择是否建立协会业务记录；协会外的安排只更新档案时，不进入寄养／领养管理列表。确认协会领养会关闭正在进行的寄养段；退养需登记实际安置交接，保留原协议与回访。具体同步、日期与历史更正规则见 [业务记录规则](BUSINESS-RULES.md)。

## 使用场景示例

### 场景一：跟进一只受伤猫咪，直到找到领养人

成员发现一只受伤的猫，先登记发现地点和受伤情况。治疗结束后如果需要寄养，视情况补充猫咪档案。选择“转寄养”，系统会建立待安置记录。找到领养人后，可继续记录领养日期、协议和后续回访；每次回访的文字与照片都会保留下来，方便下一位成员接手。

### 场景二：卖出一份猫协文创，核对库存和收入

有人在线预订一份文创，成员登记订单后，系统会预留对应数量，避免重复卖出。实际发货或自提交付时，再扣减库存并记录出库流水。订单同时关联一笔待确认收入，由财务核实收款后确认入账。

**后续计划**：接入微店 API，让店铺订单自动同步到工作台，减少逐笔录入；订单状态、商品和库存的对应关系将按平台实际开放能力逐步接入。目前仍需手动登记。

### 场景三：成员垫付猫粮费用，交给财务审核报销

成员先自行付款购买猫粮，再提交个人垫付记录，填写用途与金额。财务核对后审核，通过后进入待报销流程；实际完成报销时，再登记付款日期和已报销状态，便于区分“已经审核”和“已经付款”。

**后续计划**：如果协会已在其他表格或应用中维护报销表，可接入对应应用的 API，将报销记录同步到工作台，减少重复填写。审批和付款状态的同步需核对原应用字段与权限，目前尚未接入。

上述流程用于记录和核对，**系统不执行支付或转账**。

## 使用方法

以下两种方式都只用于本机测试，请按需要选择一种。两者的数据保存位置不同，**不会自动同步或互相迁移**。

| 方式 | 准备环境 | 访问地址 | 数据保存 |
| --- | --- | --- | --- |
| 本地模拟版 | Python 3 + 浏览器 | `http://127.0.0.1:8765/index.html` | 当前浏览器，无需登录。 |
| 本地协作版（带后端） | Node.js 24 + 浏览器 | `http://127.0.0.1:8787/` | 本机 SQLite 数据库与附件目录，需要独立账号。 |

### 方式一：本地模拟版（不带后端）

适合只想在自己电脑上体验界面与业务流程的使用者。**不需要登录、不需要创建管理员、不需要运行后端，也不需要配置数据库或安装 npm 依赖。** 页面中的“共用测试账号”只是演示身份，不是真实账号系统。

#### 1. 准备环境

准备一个现代浏览器（如 Edge、Chrome 或 Firefox）和 **Python 3**。打开终端，执行：

```sh
python --version
```

看到 `Python 3.x.x` 即可。Windows 如果提示找不到 `python`，可尝试 `py --version`；macOS / Linux 可尝试 `python3 --version`。如果都无法运行，先安装 Python 3，再重新打开终端。

#### 2. 下载并解压代码

在本仓库页面点击 **Code → Download ZIP**，将下载的压缩包完整解压。打开解压后的项目文件夹，确认能看到 `index.html`、`workspace.js`、`assets` 等文件。

**不要在 ZIP 压缩包内部直接打开页面，也不要只下载一个 `index.html`。**

#### 3. 在项目文件夹启动本地静态服务

Windows：在上述项目文件夹的地址栏输入 `powershell` 并回车，即可在该文件夹打开终端。执行：

```sh
python -m http.server 8765 --bind 127.0.0.1
```

如果前面只有 `py --version` 能运行，则改用：

```sh
py -m http.server 8765 --bind 127.0.0.1
```

macOS / Linux：打开终端，先进入解压后的项目文件夹，再启动服务；下方路径需替换为自己的实际路径：

```sh
cd "/你的解压路径/campus-cat-workbench-main"
python3 -m http.server 8765 --bind 127.0.0.1
```

看到类似 `Serving HTTP on 127.0.0.1 port 8765` 的输出后，保持终端开启。这只是供本机访问的静态文件服务，不会启动项目后端。

#### 4. 打开页面并体验

在浏览器地址栏输入：

```text
http://127.0.0.1:8765/index.html
```

页面会加载示例资料，可以尝试查看猫咪档案、新增救助、登记领养回访、调整物资库存和填写模拟账目。**请只使用虚构或充分脱敏的数据。**

每次继续体验时，在同一项目文件夹执行第3步的启动命令，再用同一浏览器打开上述地址即可。若看到文件列表或404，请检查终端是否位于包含 `index.html` 的文件夹。若端口被占用，将命令中的 `8765` 改成 `8766`，访问地址也需一起修改。

#### 5. 保存、导出、重置与退出

- **数据保存**：记录和上传附件保存在当前浏览器，不会同步给其他人。刷新通常会保留数据，但更换浏览器、使用无痕模式、清理站点数据或改变访问地址/端口，可能导致看不到原来的资料；浏览器容量不足也会影响保存。
- **导出记录**：点击右上角“管理 → 导出全部记录（不含图片）”，下载 JSON。该文件不是完整附件备份，**不包含照片与协议文件内容**。
- **重新体验示例**：点击“管理 → 恢复初始示例数据”，确认后会清除本浏览器新增和修改的演示记录。需要保留的内容请先导出。
- **关闭服务**：在启动服务的终端按 `Ctrl+C`。停止服务不会主动清空浏览器资料。

本地模拟版不提供真实账号权限、多人同步或服务器备份。若要测试独立账号、后端保存及附件权限，请使用下面的方式二。

### 方式二：本地协作版（前端 + 后端）

适合测试独立账号、角色权限、共享业务记录及附件保存的使用者。前端页面和后端 API 由同一个 Node.js 服务提供，**不需要另外启动 Python 静态服务，也不需要单独安装数据库**。此处只介绍本机测试，仍不推荐部署上线或引入真实数据。

#### 1. 准备 Node.js 与项目代码

安装 **Node.js 24**（包含 npm），然后重新打开终端，检查：

```sh
node --version
npm --version
```

`node --version` 应显示 `v24.x.x`。如果命令无法识别，请确认安装完成并重新打开终端。

与方式一相同，在仓库页面点击 **Code → Download ZIP** 后完整解压。在能看到 `package.json`、`server` 和 `login.html` 的项目文件夹中打开终端。Windows 可在该文件夹地址栏输入 `powershell` 并回车；macOS / Linux 用 `cd` 进入实际解压路径。

#### 2. 检查并启动前后端

在项目根目录依次执行：

```sh
npm test
npm start
```

当前项目没有 npm 运行依赖，**无需先执行 `npm install`**。`npm test` 通过后再执行 `npm start`；服务启动后保持终端开启。

Windows 如果提示禁止执行 `npm.ps1`，可使用以下等效命令，不需要修改系统执行策略：

```sh
npm.cmd test
npm.cmd start
```

也可以在项目根目录执行 `node server/index.cjs` 启动同一个服务。Windows 双击 `start-local.cmd` 也能启动，但不会替你运行测试。

#### 3. 访问后端入口，创建测试管理员

打开浏览器访问：

```text
http://127.0.0.1:8787/
```

**请使用根地址 `/`，不要打开 `/index.html`。** 根地址进入带后端的登录与初始化页面；直接打开 `/index.html` 仍是浏览器本地模拟版。

首次使用时，在页面创建自己的测试管理员：

- 用户名：3至40位字母、数字、下划线或连字符。
- 显示名称：填写测试用称呼。
- 密码：10至128位，使用专门的测试密码，不要复用其他网站的密码。

项目没有默认管理员或默认密码。默认本机开发配置无需初始化口令；如果已经存在账号，页面会显示登录入口，不会再次创建首个管理员。

#### 4. 测试独立账号与权限

登录后，在“管理 → 账号与权限”中新建测试账号，分配财务、领养负责人、成员或只读角色。可在同一台电脑的另一个浏览器或无痕窗口中访问同一个 `http://127.0.0.1:8787/`，登录另一账号进行测试。

这些账号连接同一个后端数据库，可以验证共享记录和不同角色的访问范围。修改本人密码或由管理员重置密码后，该账号的全部旧会话会失效，需重新登录。详细规则和管理员无法登录时的处理方法见 [账号恢复与权限矩阵](ACCOUNT-RECOVERY.md)。

默认只监听本机 `127.0.0.1`，其他人的电脑不能直接访问你的这个地址；这套步骤不包含对外部署。

#### 5. 数据保存、备份与再次启动

- **保存位置**：业务数据与账号存入项目的 `data/workbench.sqlite`，上传照片与协议存入 `data/uploads/`。本地模拟版的浏览器资料不会自动合并进来。
- **首次示例**：默认本机模式加载示例业务资料；后续启动继续使用已有数据库，不会每次重新覆盖。
- **备份**：管理员可从管理菜单创建服务器备份，或下载包含业务记录与附件的业务备份。业务备份不包含账号；完整系统备份才包含账号与权限。不要上传 `data/`、备份或密码文件到 GitHub。
- **关闭与重启**：在终端按 `Ctrl+C` 停止服务。下次仍在同一个项目文件夹运行 `npm start`，再访问 `http://127.0.0.1:8787/`，用原账号登录即可。不要删除 `data/` 文件夹。

如需测试备份恢复，可执行下面的隔离演练；它只使用临时目录与虚构资料，不读取你的实际业务数据库：

```sh
npm run drill:recovery
```

步骤及限制见 [备份恢复演练](RECOVERY-DRILL.md)。其他本机设置见 [本地协作说明](LOCAL-BACKEND.md)。

#### 6. 常见启动问题

- **找不到 `package.json`**：终端不在项目根目录，请进入包含该文件的解压后文件夹。
- **提示 `node:sqlite` 不可用**：检查 Node.js 版本，按上面的环境要求使用 Node.js 24。
- **8787 端口被占用**：先关闭自己之前启动的同一服务；或在当前终端改用另一端口，并同步修改访问地址。Windows PowerShell 示例：

```powershell
$env:PORT = "8788"
npm.cmd start
```

macOS / Linux 示例：

```sh
PORT=8788 npm start
```

此时访问 `http://127.0.0.1:8788/`。以后启动时若要继续用该端口，需要再次设置；默认仍为8787。

### 活动、赞助和公告怎么使用

- 在导航进入 **活动与赞助（测试）**，切换“活动安排 / 赞助合作”。活动默认查看即将开展的安排，可填写日期、地点、负责人、人员分工、流程和准备事项；完成时填写实际完成日期与成果。
- 赞助记录可填写合作方、协会对接人、支持内容和预计落实日期，关联具体活动；标为已落实或已结束时需要实际落实日期。赞助内容不会自动增加库存或确认财务收入，请另外核对实际到账与入库。
- 首页没有公告时，本地模拟版或后端管理员可以点击“发布公告”；已有公告时点击公告条编辑，或通过“管理公告”处理多条记录。后端只允许管理员编辑发布，其他账号只能查看已发布内容。
- 多条公告每5秒轮换。首次进入且有未读公告时弹出公告栏，关闭后同一浏览器不重复提示相同内容；新增公告或修改标题、正文后再次提醒。清理浏览器数据或更换浏览器后会重新提示；公告已读标记不是服务器阅读回执。

## 下一步更新计划

优先探索以下两项外部应用对接，**均为规划中功能，当前版本尚未实现，也暂无确定上线时间**。

| 计划 | 预期使用方式 |
| --- | --- |
| 报销表与应用 API 对接 | 对已有报销表接入其所在应用的 API，同步报销记录，并在字段和权限允许时同步审批、报销状态，减少成员和财务重复录入。 |
| 微店订单 API 对接 | 接入微店 API，将每笔可获取的店铺订单自动同步到网页工作台；逐步关联商品、订单状态、库存与待确认收入。 |

实际能同步哪些数据，取决于对应平台的 API 开放情况、账号权限及授权范围。接入时会处理重复订单、同步失败、取消与退款等情况，保留人工核对入口；外部状态同步不直接等同于财务确认入账。

#### 写入、查询与同步

- **按记录写入**：仅更新实际发生变化的业务记录，一个操作涉及的库存、收入及关联记录在同一事务内处理。
- **服务端分页**：数据库完成搜索、筛选和分页；同组物资的不同存放地点一起展示。
- **增量同步**：日常保存及轮询传输变更记录；版本过旧、跨日或变更过大时回退到完整快照。
- **并发保护**：修改附带旧版本，冲突时拒绝覆盖；幂等请求编号防止同一次提交重复记账。
- **共享规则**：后端直接调用纯业务模块，运行时不再加载界面脚本或模拟 DOM。

接口变更、验证范围与性能边界见 [升级说明](UPGRADE-NOTES.md)。为兼容早期配置，环境变量目前保留 `DANMIAO_` 前缀。

#### 后端账号能力（开发参考）

仓库另保留实验性后端代码，支持管理员、财务、领养负责人、成员和只读角色，以及本人改密、管理员重置和停服本机恢复。这些能力在方式二的本地协作版中启用，本地模拟版不启用；相关规则见 [账号恢复与权限矩阵](ACCOUNT-RECOVERY.md)。当前仍不推荐部署上线或引入真实业务数据。

#### 会话与安全

密码使用 scrypt 加盐哈希；登录采用 HttpOnly、SameSite Cookie 与 CSRF 校验。生产模式要求 HTTPS 站点来源、首次管理员初始化口令和空数据初始化，并启用 Secure Cookie。权限由服务端执行，界面按钮不是权限校验的依据。

改密、管理员重置和本机恢复会撤销目标账号的全部会话，并记录不含密码的审计；登录验证完成后会再次核对账号状态，避免并发改密后使用旧验证结果创建会话。

#### 数据目录与备份配置

默认业务目录为 `data/`，可通过 `DANMIAO_DATA_DIR` 调整。实际数据库、上传附件、密钥、日志和备份均不应提交到 Git；仓库已配置相应忽略规则。

生产配置默认每24小时在独立目录创建系统备份。快照、附件校验、停服切换和回滚流程见 [部署指南](DEPLOYMENT.md)。

### 技术边界与后续方向

当前版本定位于小规模猫协内部协作的单实例底座。首次登录仍读取一次可见业务快照，跨模块写入也会检查完整业务状态；列表查询与日常同步已分页或增量化。正式使用前仍需在实际服务器验证 HTTPS、附件上传、备份恢复与负载情况。

目前不包含在线支付、邮件找回密码、自动异地备份、对象存储或多服务器高可用。后续可继续拆分首次载入与详情查询，逐步引入类型检查，并根据实际规模评估 PostgreSQL、私有对象存储和监控告警。容器构建由 GitHub Actions 校验；实际服务器的 HTTPS 和公网运行仍需部署后验证。
